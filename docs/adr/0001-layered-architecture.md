# ADR-0001：采用六边形分层架构（L0–L4，依赖只向内）

## 状态
已接受

## 背景
目标是"一份玩法逻辑跑遍多平台多版本"。若玩法逻辑直接调用平台 API，则每个平台 / 版本都要重写，且无法纯 JVM 测试。需要一种结构，把"玩法逻辑"与"平台 / 版本胶水"彻底隔离。参考了 AllinCore 的同心分层（纯 JVM 核心 → API 门面 → 平台桥接 → 领域模块）经验。

## 决策
采用**端口-适配器（六边形）分层**，共五层、依赖只能由外向内：

- **L0 core-domain**：纯功能域，玩法逻辑 + 领域模型 + **端口接口**（声明对外界能力的诉求）。零平台依赖。
- **L1**：`core-runtime`（编排）、`core-server` / `core-client`（端公共逻辑）、`protocol`（跨端协议）。
- **L2 platform-spi**：平台抽象 SPI。
- **L3**：各平台胶水，实现 SPI、把平台 API 适配为端口实现。
- **L4**：各平台模块内的版本适配子层。

铁律：**L0 完全不知道任何下层；L0/L1 不得 import 任何平台原生类型。**

## 理由
- 玩法逻辑只写一次，跨平台/版本复用，是项目核心价值的结构保障。
- L0 零依赖 → 可纯 JVM 穷举测试（可测试性是一级质量指标）。
- 差异内聚在 L3/L4，新增平台/版本不触碰公共层（开闭原则）。

## 后果
- 正面：高内聚低耦合、可测试、可扩展；分离度可由"无平台 import + 依赖单向"机械校验。
- 负面：前期需设计端口抽象，存在一定样板代码；端口粒度设计不当会泄漏平台细节，需在评审中守住。
- 约束：依赖方向写入 [`architecture-invariants`](../../.claude/rules/architecture-invariants.md) 红线，违反即架构漂移。

## 备选方案
- **直接在各平台写玩法（无核心层）**：零抽象成本，但逻辑 N 份、不可统一测试——否决，背离项目目标。
- **仅两层（核心 + 平台）**：不足以同时容纳"编排 / 端分离 / 协议 / 版本适配"的差异维度，会让平台层臃肿成上帝模块——否决。
