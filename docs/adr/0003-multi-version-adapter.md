# ADR-0003：多版本支持用 L4 版本适配层（version-api + vX_Y）

## 状态
已接受

## 背景
需支持 Minecraft 1.12.2 → 最新（锚点 1.12.2 / 1.20.1 / 1.21.1 / 26.2；26.2 为今年最新版本号，MC 在 26.x 改用新版号方案、不再带 `1.` 前缀）且前向可扩展。跨版本 API（NMS、映射、加载器约定）漂移剧烈，若在胶水里写满版本 if-else 会迅速腐化成面条代码。

## 决策
在每个平台模块内设**版本适配子层**：
- `version-api`：声明该平台中随 MC 版本分歧的操作接口。
- `v1_12` / `v1_20` / `v1_21` / `v26_2` …：各锚点版本的实现（模块名按版本号，新方案 26.2 → `v26_2`）。
- 运行期**探测当前 MC 版本**，选择匹配的 `vX_Y` 实现装配。
- 新增一个版本 = 新增一个 `vX_Y` 模块/源集，不改公共层与既有版本实现。锚点之间的临近版本由最接近的锚点适配覆盖，必要时再细分。

## 理由
- 版本差异关在接口之后，符合开闭原则，杜绝 if-else/switch 堆砌（反模式禁令）。
- 前向可扩展：未来版本（含 26.2 及之后）只追加模块。
- 与 L3 平台轴正交：平台 × 版本两个维度各自独立扩展。

## 后果
- 正面：版本演进对玩法逻辑与公共层透明；可按需只编译所需版本，控制构建矩阵规模。
- 负面：构建矩阵随"平台 × 版本"增长，需在分期内控制（MVP 仅锚点 1.20.1，见 PRD §7）；版本探测需可靠。
- 约束：禁止在 L0–L2 出现任何版本判断；版本特判只允许在 `version-api` 实现内。
- 约束（评审）：**网络收发的通道注册 / 收发桥接也随 MC 版本漂移**（如 1.20.5+ 改 `CustomPayload`+`StreamCodec`、1.12.2 老 API、通道命名空间 1.13 起强制），属 L4 `version-api`（不只 NMS/映射）——**"protocol 字节单源 ≠ 注册管线统一"**，注册管线须经 L4 适配，不得写死在 L3 单一 net/ 里。
- 约束（评审）：**有效矩阵非笛卡尔积**——1.12.2 无 Fabric、NeoForge ≥1.20.2、Sponge 版本节奏不同；逐格标注存在性，每版本只在其真实存在的平台验证，CI 只跑锚点子集。

## 备选方案
- **多 release jar / 单 jar 反射兼容**：反射魔法难测难维护、错误延迟到运行期——否决（除非个别点无接口可抽象时受控使用）。
- **每版本一套完整代码**：复制粘贴爆炸——否决。
- **只支持单一现代版本**：不满足 1.12 起的兼容目标——否决。
